# TableFlow

Панель управления столиками ресторана: авторизация, статусы столиков, журнал событий и отправка сводки в Telegram.

## Стек

React, Vite, Tailwind CSS (CDN), Supabase Auth, Database, Realtime и Edge Functions, lucide-react.
Tailwind Play CDN предназначен для разработки; для промышленного развёртывания используйте сборку Tailwind.

## Локальный запуск

1. Установите Node.js версии, поддерживаемой используемой версией Vite, и зависимости: `npm install`.
2. Создайте `.env` по образцу `.env.example`. `VITE_SUPABASE_URL` — корневой URL проекта вида `https://<project-ref>.supabase.co`, **без** `/rest/v1/`. `VITE_SUPABASE_ANON_KEY` — публичный publishable или legacy anon key. Эти значения попадают в браузер; никогда не используйте здесь `sb_secret_` или `service_role`.
3. В Supabase настройте таблицы и политики доступа, описанные ниже. Включите Realtime для `restaurant_tables` и `activity_logs` в публикации `supabase_realtime`.
4. Запустите `npm run dev`. Адрес появится в терминале. Проверка сборки: `npm run build`.

При включённом подтверждении электронной почты пользователь должен подтвердить адрес и войти; профиль создаётся или обновляется после появления авторизованной сессии.

## Таблицы

Используется существующая схема:

| Таблица | Поля |
| --- | --- |
| `profiles` | `id` uuid (PK), `email` text, `full_name` text, `role` text, `last_active` timestamptz |
| `restaurant_tables` | `id` serial (PK), `table_number` text, `seats` int, `status` text (`free`, `occupied`, `reserved`), `updated_at` timestamptz, `updated_by` uuid |
| `activity_logs` | `id` serial (PK), `table_id` int, `action` text, `user_email` text, `created_at` timestamptz |

Для событий, не относящихся к отдельному столику, `activity_logs.table_id` должен допускать `NULL`. Нужны значения по умолчанию для идентификаторов и `activity_logs.created_at`.

### Подтверждение сотрудников и защита данных

Подготовленный скрипт `supabase/staff-access.sql` создаёт таблицу `staff_approvals`, ограничивает права клиентских ролей, настраивает политики RLS и атомарно записывает изменения статуса в журнал через триггер. Подтверждение электронной почты не означает подтверждение сотрудника. Роль в профиле не даёт доступ и не может изменяться клиентом.

1. Сделайте резервную копию базы. Проверьте структуру таблиц и существующие политики, триггеры и права, а также возможное влияние на другие приложения. Скрипт предназначен для приведённой схемы; при обнаружении существующих политик или триггеров столиков он прервётся, не изменяя их. Не отключайте эти проверки без анализа: разрешающие политики могут объединяться и случайно открыть данные.
2. Откройте Supabase → SQL Editor, выполните содержимое `supabase/staff-access.sql` целиком. До успешного выполнения скрипта и проверки доступа приложение не готово к публикации.
3. Сотрудник регистрируется и, если требуется, подтверждает почту. Администратор проверяет его личность вне приложения, копирует его UUID из Supabase → Authentication → Users и выполняет в SQL Editor:

   ```sql
   insert into public.staff_approvals (user_id)
   values ('UUID_ПОДТВЕРЖДЁННОГО_СОТРУДНИКА')
   on conflict (user_id) do nothing;
   ```

   Для отзыва доступа администратор удаляет соответствующую строку из `staff_approvals`. Клиентам не предоставлены права добавлять или удалять подтверждения. Сотрудник нажимает «Проверить снова» на экране ожидания.
4. Включите Realtime для `restaurant_tables` и `activity_logs`, проверьте отдельно доступ подтверждённого и неподтверждённого пользователей, в том числе через API. Убедитесь, что неподтверждённый пользователь не может читать или менять столики и журнал, добавлять подтверждения либо вызывать отправку в Telegram.

Ранее раскрытый секретный ключ Supabase необходимо отозвать и заменить через настройки проекта. Не добавляйте его в клиент или репозиторий.

Статистика и журнал обновляются через Supabase Realtime и после собственных изменений. При ошибке подключения к Realtime интерфейс сообщает об этом.

## Публикация на GitHub и Vercel

1. Создайте на GitHub пустой репозиторий `SmartService` без добавления README или `.gitignore`: они уже есть в проекте. Выберите публичную или приватную видимость осознанно. Файл `.env` не должен попасть в репозиторий.
2. В терминале из корня проекта привяжите репозиторий и отправьте ветку `main`, заменив `ИМЯ_ПОЛЬЗОВАТЕЛЯ` на свой логин GitHub:

   ```sh
   git remote add origin https://github.com/ИМЯ_ПОЛЬЗОВАТЕЛЯ/SmartService.git
   git push -u origin main
   ```

   Если Git запросит авторизацию, выполните её через стандартное окно Git Credential Manager. Не вставляйте токены в команду или URL.
3. Войдите в Vercel, импортируйте репозиторий, выберите Vite и добавьте переменные `VITE_SUPABASE_URL` и `VITE_SUPABASE_ANON_KEY` из локального `.env` в настройки проекта. Используйте только публичный ключ. Запустите развёртывание.
4. В Supabase → Authentication → URL Configuration укажите опубликованный адрес как Site URL и добавьте его в Redirect URLs. Для локальной проверки также добавьте адрес локального сервера Vite.
5. Проверьте регистрацию, подтверждение почты, подтверждение сотрудника администратором, вход, смену статуса, журнал и обновления между двумя сессиями. Проверьте, что неподтверждённый пользователь не имеет доступа к данным через API. Отдельно настройте Edge Function, если нужна отправка в Telegram.

## Отправка в Telegram

Создайте бота через BotFather, добавьте его в чат менеджеров и получите идентификатор чата. Токен бота и идентификатор чата хранятся **только** в секретах Edge Function. Не помещайте токен в `.env` фронтенда и не отправляйте его в чат.

В настройках секретов Edge Functions в панели Supabase задайте `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID`. Установите и авторизуйте Supabase CLI, затем из корня проекта выполните:

```sh
supabase init
supabase link --project-ref <project-ref>
supabase functions deploy telegram-summary --no-verify-jwt
```

Вводите секреты безопасным способом, не публикуйте историю команд и не добавляйте их в репозиторий. Для проекта из `.env` идентификатор проекта — часть URL перед `.supabase.co`. Функция проверяет авторизацию и подтверждение сотрудника, заново считает доступные ему свободные столики и отправляет сообщение через Telegram Bot API. Событие в журнал добавляется серверным клиентом с автоматически предоставляемым Supabase `SUPABASE_SERVICE_ROLE_KEY`; этот ключ не должен попадать в браузер. Успех отображается только после подтверждения Telegram; если запись в журнал не удалась, показывается отдельное предупреждение. При отсутствии развёрнутой функции или её секретов отправка не работает.

Параметр `--no-verify-jwt` отключает проверку шлюза, принимающую только JWT с устаревшей подписью. Сама функция обязательно проверяет сессию через `auth.getUser()` и подтверждение сотрудника; не удаляйте эти проверки.

Кнопка доступна подтверждённым сотрудникам. Для ограничения отправки менеджерами добавьте серверную проверку роли и соответствующие политики. Для защиты от злоупотреблений при публичной регистрации настройте ограничения доступа и частоты запросов.
